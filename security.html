SECURITY MODEL

Security you can audit

No agents, no phone-home, no hidden accounts. MurOS authenticates against the system you already trust, ships locked down by default, and never applies a change that can lock you out without a way back.

Authentication

One identity for the box, not a parallel user store bolted onto a web app.

PAM, shared with SSH

The web UI logs in through PAM against the local Linux account, the same credentials as SSH. There is no separate application password and no password hash stored in the MurOS database.

No default admin account

You log in as root with the password root already has. MurOS creates no admin user, never resets the root password and never forces a change at first login.

Per-account UI access

Passing PAM is not enough on its own. Only root reaches the UI by default. Other Linux accounts stay blocked until root explicitly grants access from Access > Users.

Stateless sessions

Sessions are signed JWT (HS256). The signing secret lives in a 0600 key file on the appliance, readable by root only. Every API route except login and health requires a valid token.

Secure by default

A fresh install is closed, not open. You open things up deliberately, from the UI.

Deny by default

Input and forward policies drop. The WAN is closed inbound out of the box. A built-in anti-lockout rule keeps the management interface (HTTPS, SSH, ICMP) reachable from trusted zones so you never fence yourself out.

SSH closed on install

openssh-server is present but the SSH service is disabled on a fresh install. When enabled, root login is key-only (prohibit-password), with keys kept in the account home.

Kernel hardening and fail2ban

A sysctl hardening drop-in and fail2ban are enabled by default, so brute-force attempts against exposed services are rate-limited and banned without extra setup.

Inert services until configured

Daemons that need a per-site config (VPN, HA, conntrack sync, watchers) stay disabled until you apply a configuration from the UI. Nothing listens that you did not ask for.

Safe changes

Every change is staged, previewed and reversible. A bad ruleset should not cost you a site visit.

Dry-run preview

The generated nftables ruleset is shown before it is applied. You see exactly what will load into the kernel.

Apply with auto-rollback

After applying, a ten-second confirmation countdown runs. If the new ruleset breaks your session, the previous state is restored automatically.

Full audit log

Every write action through the UI is recorded: user, method, path, status, source IP and a payload digest. You can answer who changed what, and when.

Snapshots and backups

One-click snapshots capture the database, the nftables ruleset and the network config. Push them off-box over SSH, FTP or rclone, and restore any snapshot. Upgrades take an automatic pre-upgrade snapshot.

Transparent and auditable

Open source, no phone-home

The whole codebase is AGPL-3.0 and public. There is no telemetry, no license check and no outbound call other than the apt updates you trigger.

Signed updates

Packages come from a signed apt repository, verified by a pinned keyring. Updates flow through standard apt, so your existing patch process applies.

Standard config paths

MurOS writes to standard Debian drop-in locations and never touches the system network files directly. Configuration is generated from one source of truth, so what is on disk matches the UI.

Read-only standby in HA

In a high-availability pair the standby node is read-only and mirrors the master config, so a failover keeps the full ruleset without a divergent second copy to manage.

Reporting a vulnerability

Found a security issue? Please report it privately rather than opening a public issue, so a fix can ship before details are disclosed. Use GitHub private vulnerability reporting, or email security@muros.org. We acknowledge reports within five business days and credit reporters who want it.
